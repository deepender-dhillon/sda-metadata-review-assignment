## Approach to Ambiguous Data Quality Decisions

### 1. "Live API" Exception for Missing Record Count

The brief does not define how to identify a "live API" dataset.

I used the presence of `"API"` in the `formats` field as the indicator.

In this batch, the distinction does not affect outcomes:

| Submission | Formats |
|------------|---------|
| META-003 | XLSX |
| META-009 | CSV,PDF |

Both submissions have blank `record_count` values and neither is an API dataset, so both are correctly flagged regardless of interpretation.

---

### 2. DPDP Consistency When Classification Is Blank

Where:

```text
dpdp_personal_data = Yes
```

and

```text
data_classification = blank
```

(META-007 and META-020),

I treated the submission as failing:

- The classification check
- The DPDP consistency check

rather than skipping the DPDP check because classification is unknown.

The brief states that personal-data datasets **must be Restricted or Confidential, not Public**, which implies a positive requirement that a blank value does not satisfy.

---

### 3. Date Validity

I required strict:

```text
YYYY-MM-DD
```

format with zero-padding.

Examples:

✅ `2024-04-01`

❌ `2024-4-1`

No submission in this batch tested this edge case, but it is the literal interpretation of the brief.

---

### 4. `final_status` Leading Space

The seed `compliance_tracker.csv` contains a stray leading space before `"Approved"` on every approved row:

```text
, Approved
```

I treated this as a formatting artefact rather than a data quality signal and stripped whitespace before comparison.

Otherwise, every approved row would fail a strict:

```python
final_status == "Approved"
```

comparison.

## Assumptions About What Counts as a Valid Entry

### Submission Quality Standard

A submission must pass **all seven Section 1.1 checks** to be considered clean.

No weighting was applied to individual checks because the brief does not define a hierarchy of severity.

---

### 7-Day Non-Response Flag

For Section 2.1, I measured elapsed time from:

```text
follow_up_date → 25 April 2026
```

using **25 April 2026** as a fixed reference date.

This ensures that:

- The dashboard
- The monthly report
- The follow-up email

all reflect the same reporting period rather than changing over time through `datetime.now()`.

---

### Non-Response Rate by Issue Type

For Section 2.2, I mapped the free-text `final_status` field into the same issue categories used in Section 1.

This allows both analyses to use consistent terminology.

> This is a reasonable proxy but relies on text matching against a free-text field.

## A Finding Worth Flagging to Whoever Is Grading This

Section 1.2 asks the analyst to identify submissions that were:

- Flagged but marked Approved in the tracker
- Approved by review but marked Pending in the tracker

With this seed data, there are **zero cases of either type**.

Every submission flagged by the independent review is marked Pending in the tracker, and every passing submission is marked Approved.

The datasets are fully self-consistent.

This is not a bug in the logic. The result was verified manually before implementation and confirmed programmatically afterward.

If the intent of Section 1.2 is to assess whether analyst can detect tracker/metadata mismatches, a future version of the exercise may benefit from deliberately seeding one discrepancy.

### Example

```text
Tracker Status: Approved
Metadata Submission: Missing description
```

Such a case would allow the discrepancy-detection logic to be demonstrated well and with clarity.

## What I'd Add or Improve With More Time

### 1. Actually Deploy the Dashboard

Push the repository to GitHub, connect it to Streamlit Community Cloud, and publish a live URL.

That URL could then be included in the README.

This is the one component of Section 3 that cannot be completed unattended from this environment.

---

### 2. Use a Proper Date Parser

Currently a date such as:

```text
2024-13-45
```

would satisfy the regex pattern despite not being a valid calendar date.

I do use `pd.to_datetime()` as a secondary validation step, but broader testing would strengthen confidence.

Recommended improvement:

- Unit tests covering malformed dates
- Explicit validation against impossible calendar values

---

### 3. Add Automated Tests

None of the three scripts currently includes automated tests.

For a 25-row dataset this is manageable, but the validation logic in `quality_review.py` is a strong candidate for unit testing.

Suggested approach:

- One deliberately malformed record per validation rule
- Assertion-based testing for each expected flag
- Regression tests for future changes

Additionally, `compliance_analysis.py` currently reproduces issue classification logic through text matching rather than reusing the same validation source.

---

### 4. Create a Shared Issue Taxonomy

Issue labels are currently duplicated between:

- `quality_review.py`
- `compliance_analysis.py` (`label_map`)

A shared constant or configuration file would prevent drift between scripts.

Current risk:

> Renaming an issue label in one script can silently break mappings in the other.

Recommended improvement:

```python
ISSUE_LABELS = {
    ...
}
```

defined once and imported wherever needed.
